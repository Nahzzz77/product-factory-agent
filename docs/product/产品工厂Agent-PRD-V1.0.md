## 2. 产品概述

### 2.1 产品定位

产品工厂 Agent 是运行在本地编程 Agent 环境中的项目交付系统。它接收一份已经由产品负责人确认的 PRD，从零创建 Web 产品，并按标准阶段完成技术适配、开发、系统验证、人工验收、正式前端、可部署准备和经授权的协助式上线。

产品工厂不是一个独立 Web 平台，也不是一段一次性生成整个项目的超长提示词。V1 由以下部分组成：

- 通用流程内核；
- 文件化项目状态机；
- 确定性检查与证据脚本；
- Codex、Claude Code、Pi 三个薄入口；
- AI Web 与运行时图像两个产品适配器；
- 项目模板、文档模板和版本记录；
- 阶段内自主、跨阶段人工确认的门禁机制。

### 2.2 核心价值

在缺少前端、后端、设计和运维人员支持的情况下，让产品经理能够以“一人 + AI”的方式，按照可追溯、可验收、可恢复的标准流程，把一份已确认 PRD 推进为可运行、可验证、可交接、可部署的产品。

### 2.3 核心原则

1. PRD 是业务事实来源，工程手册是规则来源，二者不得混淆。
2. Agent 在当前阶段内可以自主分析、编码、测试和修复。
3. 没有产品经理明确批准，Agent 不得跨阶段。
4. 系统验证通过不等于产品验收通过，模型效果和用户体验必须人工确认。
5. 项目状态、审批和证据写入仓库文件，不依赖聊天记录。
6. 默认准备到“可部署”，正式上线、付费资源和生产操作必须单独授权。
7. 公共流程与产品类型适配器解耦，后续可增加游戏、语音等适配器。

## 3. 背景与问题

### 3.1 背景

AI 原生团队常由一名产品经理同时负责多个项目，且未必有稳定的开发、设计或运维资源。编程 Agent 已能完成大量编码工作，但常见使用方式仍存在以下问题：

- 依赖当前聊天上下文，换会话或换工具后难以恢复；
- 容易跳过需求确认、真实运行和人工验收；
- 把构建成功或 Mock 测试通过误判为产品完成；
- 技术决策、版本、验收和遗留问题没有持续留痕；
- 外部模型、图像、云资源和部署涉及成本与安全，却缺少统一门禁；
- 不同编程 Agent 各自形成流程，难以跨工具接续。

### 3.2 要解决的问题

产品工厂需要把“会写代码的 Agent”提升为“受阶段、证据和人工审批约束的项目交付 Agent”，并回答：

- 当前项目处于哪个阶段；
- 当前阶段允许 Agent 做什么；
- 阶段完成需要哪些可复核证据；
- 哪些结论必须由产品经理确认；
- 失败、中断或更换工具后如何继续；
- 哪些外部操作需要额外权限和费用批准；
- 新成员如何通过项目文件理解历史和现状。

## 4. 目标与非目标

### 4.1 V1 产品目标

1. 从一份已确认 PRD 初始化一个全新的 Web 产品项目。
2. 在 Codex、Claude Code、Pi 中执行同一套阶段协议。
3. 支持常规 AI Web 产品及用户运行时生成图片的产品。
4. 用结构化状态、证据和人工审批阻止 Agent 自行越过阶段。
5. 自动维护技术适配、阶段开发、验收、发布和变更文档。
6. 支持会话中断和跨工具接续，不丢失已写入项目的上下文。
7. 默认交付到本地验收完成或可部署状态；经明确授权后协助上线。

### 4.2 V1 非目标

- 不从模糊想法自动生成并批准 PRD；
- 不接管或自动改造已有遗留项目；
- 不支持原生 App、小程序和桌面客户端；
- 不包含轻量游戏适配器，后续按真实游戏 PRD 增加；
- 不支持大型 3D、实时多人、MMO 等复杂游戏生产；
- 不自建 GPU 图像模型；
- 不承诺适配高并发、多地域容灾或强监管生产系统；
- 不替代产品经理判断模型内容质量、视觉质量和产品价值；
- 不允许无人确认创建付费资源、公开上线或操作生产数据；
- 不承诺一次对话生成完整生产系统。

## 5. 用户与使用场景

### 5.1 目标用户

主要用户是负责从需求到交付全过程的 AI 产品经理、AI 原生团队负责人或独立产品创建者。用户可以不具备完整工程经验，但能够：

- 提供一份已确认 PRD；
- 对范围、费用、安全和平台做业务决策；
- 按清单亲自完成阶段验收；
- 在注册、实名、凭证录入和正式发布时完成本人操作；
- 对模型效果、视觉质量和用户体验负责。

### 5.2 典型场景

1. 从零开发文本生成、多轮对话、结构化生成或工作流 Agent。
2. 开发包含 RAG、文件上传和长任务的 AI Web 产品。
3. 开发用户在产品运行时进行文生图、图生图或图片编辑的产品。
4. 在 Codex 中开始项目，随后使用 Claude Code 或 Pi 从文件状态继续。
5. 本地验收完成后生成可部署包，或经授权协助部署至测试或正式环境。

## 6. 输入、输出与资料优先级

### 6.1 项目输入

每个新产品项目至少提供：

```text
inputs/
├── PRD.md
├── constraints.md
└── assets/
```

- `PRD.md`：已确认的产品需求基线；
- `constraints.md`：预算、模型、平台、期限、合规等约束，没有时可为空；
- `assets/`：设计稿、参考图片和其他产品资料，按需提供。

产品工厂仓库统一维护三份工程手册及其版本信息，项目初始化时记录所使用的手册版本和校验值。

### 6.2 PRD 最低信息要求

PRD 应明确：

1. 目标用户与核心任务；
2. 输入、处理过程和最终产物；
3. 用户主流程及人工确认点；
4. 功能范围、MVP 和阶段优先级；
5. Agent 或产品效果验收标准；
6. 模型、费用、平台和交付终端约束；
7. 数据、隐私、性能和部署要求。

会显著改变体验、成本、安全或范围的缺项必须询问。普通技术细节由产品工厂采用默认方案，并在技术适配声明中显式记录。

### 6.3 资料优先级

发生冲突时按以下顺序处理：

1. 产品负责人本轮明确确认的决定；
2. 当前已确认 PRD 与验收标准；
3. 已确认设计稿和交互说明；
4. 已确认接口契约和真实后端能力；
5. 当前项目代码和工程约束；
6. 产品工厂适配器默认方案；
7. 三份工程手册中的普通默认建议。

安全、隐私、数据保护、可恢复性和验收真实性等强制底线不能被普通 PRD 静默覆盖。

### 6.4 项目输出

每个项目至少保留：

- PRD 基线与变更记录；
- 项目接收报告；
- 技术适配声明；
- 分阶段开发文档；
- 自动测试、真实运行和模型验证证据；
- 人工验收报告与审批记录；
- 发布准备、发布记录和回退信息；
- 当前项目状态、已知问题和下一步；
- README 与 CHANGELOG。

## 8. 启动与恢复

### 8.1 固定启动方式

用户通过固定启动指令明确触发工厂。Agent 不因目录中出现 PRD 而自动开工。

启动后依次执行：

```text
检查 inputs/
→ 验证 PRD 已确认及最低信息
→ 识别适配器
→ 检查本机环境与 Git
→ 生成项目接收报告
→ 生成技术适配声明
→ 等待首次人工确认
```

### 8.2 中断恢复

新会话执行固定继续指令后，必须：

1. 读取 `state.json`；
2. 检查当前阶段文档；
3. 检查 Git 状态与未提交差异；
4. 检查最近一次仍有效的验证证据；
5. 判断是否正在等待人工批准；
6. 输出恢复摘要；
7. 从未完成步骤继续，不重复初始化。

### 8.3 跨工具接续

Codex、Claude Code 和 Pi 共用同一套：

- 项目状态；
- 阶段文档；
- 审批记录；
- 证据目录；
- Git 仓库；
- 适配器协议。

工具入口只处理工具调用差异，不能改变公共阶段协议。Pi 入口提供 DeepSeek 配置示例，但公共内核不绑定具体模型。

## 9. 阶段状态机

### 9.1 主流程

```text
initialized
→ inputs_checked
→ adaptation_pending_approval
→ stage_development
→ system_verification
→ human_acceptance_pending
→ next_stage_or_frontend
→ release_ready
→ deployment_pending_approval
→ deployed_pending_acceptance
→ production_accepted
→ observing
```

项目可以按 PRD拆分多个 `stage_development → system_verification → human_acceptance_pending` 循环。

### 9.2 阶段内自主执行

在已批准的当前阶段内，Agent 可以：

- 分析和补全阶段技术文档；
- 创建和修改本地代码与文档；
- 运行测试、构建和浏览器检查；
- 在预算与数据边界内调用已批准的真实模型；
- 根据验证结果反复修复；
- 更新当前阶段证据和已知问题。

### 9.3 跨阶段人工确认

标准批准指令为：

```text
验收通过，批准进入下一阶段。
```

人工可以给出三种结论：

- 验收通过并批准进入下一阶段；
- 验收不通过，附现象、截图或反馈，留在当前阶段修复；
- 带已知问题验收通过，必须记录问题、影响和后续处理阶段。

安全、密钥、数据丢失、权限隔离、核心流程仍使用 Mock 等强制底线不得通过“带问题验收”绕过。

### 9.4 开发路线

- 后端先行：适合提交任务后等待结果、后端能力可独立验证的产品；
- 纵向切片：适合多轮对话、图片生成、人工确认、画布等界面参与核心价值的产品。

Agent必须在技术适配声明中选择路线并说明原因。

## 10. 人工门禁

V1包含六类门禁：

| 门禁 | 人工确认内容 |
| --- | --- |
| 技术适配门禁 | 产品理解、费用、平台、范围和暂缓项 |
| 阶段验收门禁 | 当前阶段真实用户任务能否完成 |
| 模型效果门禁 | 文本或图像输出是否达到 PRD 标准 |
| 前端体验门禁 | 桌面、移动端、异常和恢复是否可用 |
| 部署门禁 | 费用、云资源、权限、数据和回退方案 |
| 线上验收门禁 | 公网核心闭环、登录、隔离、持久化和监控 |

Agent在门禁处必须暂停，展示验收入口、证据摘要、已知问题和下一阶段影响，不能自行模拟产品经理批准。

## 11. 验证与证据

### 11.1 三层完成状态

```text
implemented       代码已实现
system_verified   自动检查和真实运行证据通过
human_accepted    产品经理亲自操作并批准
```

只有 `human_accepted` 才能跨阶段。

### 11.2 证据结构

```text
.product-factory/evidence/stage-02/
├── manifest.json
├── test-results/
├── runtime-checks/
├── browser/
├── model-evaluation/
└── known-issues.md
```

`manifest.json` 至少记录：

- PRD、工厂和适配器版本；
- 对应 Git 提交或工作树标识；
- 执行命令、时间、退出状态与摘要；
- 本地访问地址或测试入口；
- 浏览器、尺寸和核心路径；
- Mock 或真实模型标记；
- 已知问题与严重程度；
- 是否具备人工验收条件。

相关代码在验证后发生变化时，受影响证据视为过期，必须重新验证。

### 11.3 自动验证范围

- 后端单元、接口、状态流转和错误路径测试；
- 前端 Lint、类型检查、组件测试和生产构建；
- 至少一条端到端核心业务流程；
- 服务启动与健康检查；
- 浏览器 Console、失败请求和重复请求检查；
- 桌面与移动端布局；
- 刷新、断线、重试和恢复；
- 密钥、敏感文件和构建产物检查；
- 项目需要时的数据恢复与权限隔离验证。

### 11.4 模型验证

涉及模型的能力必须区分：

```text
Mock 自动测试
+ 真实模型冒烟
+ 产品经理效果验收
```

Agent只能判断结构、错误、延迟、费用和明显异常，不能替代人工判断内容价值或视觉质量。

### 11.5 人工验收清单

每次提交人工验收时必须写清：

1. 打开什么地址；
2. 输入什么测试内容；
3. 应该看到什么；
4. 如何测试失败和恢复；
5. 哪些项目需要主观判断；
6. 发现问题时需要提供什么截图或现象。

证据不得保存密钥、完整敏感文档或不必要的用户隐私。

## 12. 产品类型适配器

### 12.1 统一适配器协议

每个适配器必须声明：

- 适用条件；
- 所需输入；
- 推荐开发路线；
- 新增阶段；
- 技术能力；
- 文档模板；
- 人工验收项；
- 自动检查项；
- 费用与安全风险；
- 部署约束。

新增适配器不得修改公共审批语义和强制底线。

### 12.2 AI Web 基础适配器

支持：

- 默认 FastAPI 后端与 Next.js Web 前端；
- 文本生成、多轮对话和结构化输出；
- RAG、文件上传和任务工作流；
- 模型配置、超时、有限重试和输出校验；
- 任务状态、人工确认和刷新恢复；
- Mock 测试、真实模型冒烟和浏览器验收。

默认方案必须根据 PRD、当前稳定版本和环境生成技术适配声明，不得将手册中的版本机械写死。

### 12.3 运行时图像适配器

当 PRD出现文生图、上传参考图、图生图或图片编辑时，与 AI Web 适配器组合使用。

必须支持：

- 外部图像模型统一接口；
- 异步生成任务、状态查询、幂等和有限重试；
- 原图、参考图、结果图和缩略图管理；
- 对象存储与访问权限；
- Prompt、模型、参数和版本追踪；
- 内容安全、隐私和图片删除；
- 单次成本、用户额度和防重复生成；
- 固定样例集与人工视觉验收。

统一能力接口至少包含：

```text
textToImage()
imageToImage()
editImage()
getTaskStatus()
cancelTask()       # 供应商支持时
estimateCost()
```

具体项目首次可以只实现一家供应商，但业务代码不能散落供应商专属字段。公共内核不得写死供应商。

图像能力接入完整业务流程前，需要完成：

```text
固定测试样例
→ 少量批量生成
→ 检查主体、风格、失败率、耗时和费用
→ 产品经理确认视觉质量
→ 接入完整用户流程
```

### 12.4 后续游戏适配器

V1不开发游戏适配器。后续以真实小游戏 PRD为输入，新增最小可玩循环、游戏状态、存档、数值配置、浏览器性能、触控和人工试玩验收等规则。公共状态机、审批、证据、版本和部署能力应可直接复用。

## 13. PRD变更与版本管理

### 13.1 PRD变更

Agent不得静默改变需求。反馈改变目标用户、核心流程、范围或验收标准时：

```text
发现需求变化
→ 生成变更申请
→ 写明原因、受影响阶段、成本和建议
→ 产品经理确认
→ PRD版本升级
→ 重新评估受影响阶段和证据
```

### 13.2 版本关联

每份派生文档和证据至少关联：

- PRD版本；
- 产品工厂版本；
- 适配器及版本；
- Git提交或工作树标识；
- 生成时间；
- 当前阶段状态。

审批历史只追加，旧验收报告不得覆盖。

## 14. 异常、并发与回退

### 14.1 异常分类

| 类型 | 含义 |
| --- | --- |
| `input_required` | 缺少会改变范围、安全或费用的信息 |
| `approval_required` | 等待产品经理验收或授权 |
| `implementation_failed` | 代码、测试或构建尚未通过 |
| `external_service_failed` | 模型、网络或云服务故障 |
| `environment_blocked` | 本机依赖、端口或权限问题 |
| `policy_blocked` | 触犯安全、隐私或费用底线 |
| `interrupted` | 会话或进程意外中断 |

异常记录必须包含发生步骤、已完成事项、失败证据、文件或外部资源变更、已尝试方法、重试安全性和需要产品经理采取的动作。

### 14.2 并发保护

同一产品项目同一时间只允许一个 Agent执行写操作。项目保存运行锁和执行记录。发现有效写锁时，新 Agent只能检查状态，不能并发修改。异常中断后通过明确接管流程处理过期锁，并保留原执行记录。

### 14.3 回退

- 每个阶段开始前建立 Git检查点；
- 阶段验收通过后建立可追溯版本点；
- 外部部署前记录当前线上版本和回退方法；
- 数据库回退必须有独立迁移和恢复方案；
- 未通过人工验收的阶段不得覆盖最后一个已验收版本。

## 15. 权限、安全与费用

### 15.1 权限级别

| 级别 | 操作 | 默认策略 |
| --- | --- | --- |
| P0 | 读取项目、分析 PRD、检查状态 | 可自主执行 |
| P1 | 修改本地代码和文档、运行测试 | 当前阶段内可自主执行 |
| P2 | 调用真实模型、上传测试素材 | 供应商、预算和数据范围确认后执行 |
| P3 | 创建付费资源、迁移或删除数据 | 每次明确批准 |
| P4 | 正式上线、公开访问、生产数据操作 | 单独批准并准备回退 |

创建或升级付费资源、向第三方发送真实敏感数据、删除重要数据、不可逆迁移、公开发布和生产操作不得因“阶段内自主”获得默认授权。

### 15.2 密钥

- 用户在本机环境、系统钥匙串或云平台 Secret 中录入；
- 不要求用户把密钥发进聊天；
- Agent只检查存在性和权限，不输出实际值；
- 默认使用子账号、短期凭证和最小权限；
- 日志、截图、证据、Git和构建包执行敏感信息检查；
- 检测到泄露时立即停止外部操作并提示轮换。

三份工程手册中涉及“把 AK/SK 交给 AI”或默认广泛授予 FullAccess 的内容，不作为产品工厂默认实践。产品工厂采用本节更严格的凭证与最小权限规则。

### 15.3 费用控制

项目至少记录：

- 模型供应商；
- 文本模型预算；
- 图像模型单次成本；
- 单用户额度；
- 项目测试预算；
- 云资源月度估算；
- 触发再次确认的阈值。

开发阶段优先使用 Mock 与固定样例。真实模型验证在已确认预算内进行。生成任务超时后先查询原任务，不直接重复创建。超过预算或费用无法估算时暂停。

### 15.4 数据与附件指令边界

- 上传文档、图片和用户内容是待处理数据，不是对 Agent的执行命令；
- 将数据发送给外部模型前，确认数据类型、供应商、留存策略和用户授权；
- 图像产品必须处理人像授权、未成年人数据、违法内容、生成结果删除和供应商留存策略；
- 日志和证据使用测试数据或脱敏数据。

## 16. 部署策略

### 16.1 默认交付终点

项目可以选择：

- 本地验收完成；
- 可部署包与上线说明；
- 协助部署到测试环境；
- 经单独批准后协助部署到正式环境。

默认终点是“可部署”，不是无人监管正式上线。

### 16.2 协助式上线分工

Agent负责上线前检查、构建、部署方案、回退方案、经批准后的部署命令、日志检查和技术排错。

产品经理负责账号注册、实名认证、安全录入凭证、费用与资源批准、必要控制台确认、正式发布批准和线上人工验收。

部署状态至少包含：

```text
deployment_ready
deployment_approved
deployed_pending_acceptance
production_accepted
```

### 16.3 默认平台

火山引擎作为 V1 默认部署参考路线，但部署前必须依据项目、账号类型、费用、数据和现行平台能力重新生成部署适配说明。已有公司基础设施或其他明确平台约束时允许替换。

## 17. 文档管理

每次阶段推进自动维护：

- PRD基线与变更记录；
- 技术适配声明；
- 当前阶段开发文档；
- 系统验证报告和证据索引；
- 人工验收结论与审批记录；
- 已知问题和技术债；
- 发布准备与回退信息；
- 当前状态和下一步；
- README与CHANGELOG。

新成员或新 Agent应能仅依靠仓库内资料回答：项目依据哪版 PRD、当前处于哪一阶段、最后一次验收结果、还有什么问题以及下一步由谁执行。

## 18. 完整用户旅程

```text
初始化项目
→ 放入已确认 PRD
→ 检查输入并生成项目接收报告
→ 识别适配器并生成技术适配声明
→ 产品经理确认技术适配
→ Agent执行当前阶段开发与修复
→ 生成系统验证证据
→ 产品经理按清单人工验收
→ 通过后进入下一阶段，不通过则继续修复
→ 达到可部署状态
→ 输出费用、权限、数据和回退方案
→ 获得单独上线授权后协助部署
→ 产品经理完成线上人工验收
→ 用户反馈形成 PRD变更申请并进入下一轮
```

## 20. 成功指标与验收标准

### 20.1 流程可靠性

- 能从已确认 PRD初始化新项目；
- 能识别 AI Web 和运行时图像需求；
- 未经人工批准不能跨阶段；
- 中断后能从文件状态恢复；
- 能在 Codex、Claude Code、Pi 之间切换；
- 能区分实现完成、系统验证和人工验收；
- 能关联 PRD、代码、证据和审批版本；
- 同一项目不会被两个 Agent并发写入。

### 20.2 交付质量

- 至少一个示例项目完成一条真实用户闭环；
- 每个交付阶段有结构化证据和普通人可执行的验收清单；
- 核心功能不能依靠 Mock冒充完成；
- 前端完成真实浏览器和移动端检查；
- 模型能力完成 Mock、真实冒烟和人工效果验收分层；
- 已知问题、未完成项和回退方法透明记录。

### 20.3 安全与成本

- 密钥不进入聊天、日志、仓库、前端或证据；
- 未经批准不创建付费资源、不正式上线、不操作生产数据；
- 外部模型调用受预算、数据和供应商边界约束；
- 图像任务具备成本记录、防重复和内容安全机制。

## 22. 待审阅结论
