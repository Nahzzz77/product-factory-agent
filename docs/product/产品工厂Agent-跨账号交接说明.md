## 已确认的产品定义

产品工厂 Agent 是一个运行在本地编程 Agent 环境中的项目交付系统。它接收一份已经确认的 PRD，从零创建 Web 产品，并以“阶段内自主、跨阶段人工确认”的方式完成技术适配、开发、验证、前端、可部署准备和经授权的协助式上线。

它的重点不在于一次性生成全部代码，而在于让项目过程可追溯、可验收、可恢复、可交接。

## 已确认的 V1 边界

V1 要支持：

- 从零创建 Web 产品；
- 输入已经确认的 PRD，不负责把模糊想法自动变成已批准 PRD；
- Codex、Claude Code 和 Pi 三个执行入口；
- Pi + DeepSeek 的配置示例；
- 常规 AI Web 产品；
- 用户在最终产品运行时使用的文生图、图生图和图片编辑能力；
- 文本生成、多轮对话、结构化生成、RAG、文件处理和工作流；
- 文件化项目状态、阶段证据、人工验收、版本记录和恢复；
- 火山引擎作为默认部署参考路线；
- 默认交付到本地验收完成或可部署状态，经明确授权后协助部署。

V1 暂不支持：

- 接管已有遗留项目；
- 原生 App、小程序和桌面客户端；
- 自动批准 PRD；
- 无人审批创建付费资源、公开上线或操作生产数据；
- 自建 GPU 图像模型；
- 轻量游戏适配器；
- 大型 3D、实时多人、MMO、高并发或强监管产品。

后续要做卡片养成小游戏时，再基于真实游戏 PRD 增加“轻量 Web 游戏适配器”。公共状态机、审批、证据、版本和部署能力应复用，当前不提前实现游戏规则。

## 运行和交付形态

产品工厂本身是一个独立项目仓库，包含：

```text
product-factory-agent/
├── core/                 公共状态机、适配器协议和数据格式
├── skills/               Codex、Claude Code、Pi 入口
├── adapters/             ai-web 与 image-runtime
├── templates/            技术适配、阶段开发、验收、发布和变更模板
├── scripts/              输入、状态、证据和审批检查脚本
├── references/handbooks/ 三份工程手册与版本信息
├── examples/             最小示例项目
└── README.md
```

每个被工厂创建的产品项目需要拥有：

```text
inputs/                   PRD、约束和设计资产
.product-factory/         state.json、project.yaml、审批和证据
docs/                     技术文档、验收、发布记录和 CHANGELOG
backend/
frontend/
README.md
```

结构化文件是 Agent 和脚本的流程事实来源，Markdown 是给产品经理和团队阅读的记录。聊天记录不能代替落盘状态。

## 关键工作方式

用户通过固定指令启动新项目。Agent 先检查输入、PRD 状态、适配器需求、环境和 Git，再生成项目接收报告与技术适配声明。首次技术适配必须由产品经理确认。

Agent 在已经批准的当前阶段内可以自主分析、编码、运行测试、真实运行、浏览器检查和修复。阶段结束时必须生成证据和普通人可执行的验收清单，并暂停等待人工结论。

唯一标准批准语句为：

```text
验收通过，批准进入下一阶段。
```

人工可以：

- 验收通过并批准进入下一阶段；
- 验收不通过，附现象、截图或反馈，Agent 留在当前阶段修复；
- 带已知问题验收通过，必须记录问题、影响和未来处理阶段。

安全、密钥、数据丢失、权限隔离、核心流程仍为 Mock 等强制底线不能通过“带问题验收”绕过。

## 状态与验证要求

每个阶段的完成状态分为：

```text
implemented       代码已经实现
system_verified   自动检查和真实运行证据通过
human_accepted    产品经理已经实际操作并批准
```

只有 `human_accepted` 才能跨阶段。

验证必须包含与项目相关的后端测试、前端 Lint、类型检查、构建、至少一条端到端闭环、真实浏览器检查、桌面和移动端检查、失败与恢复检查。模型功能必须明确区分 Mock 测试、真实模型冒烟和产品经理的效果验收。

图像产品的图像模型只负责生成插画或图片结果。文字、数字、卡框、图标和严格版式应由确定性程序合成，不能依赖图像模型生成整张带文字的卡片。图像适配器需要处理异步任务、对象存储、成本、额度、重试、内容安全、隐私、删除和人工视觉验收。

## 权限、密钥与上线

权限分层：

- P0 读取和分析可以自主执行；
- P1 当前阶段内修改本地代码和运行测试可以自主执行；
- P2 调用真实模型或上传测试素材，需要已确认供应商、预算和数据边界；
- P3 创建付费资源、迁移或删除数据，每次都要明确批准；
- P4 正式上线、公开访问和生产数据操作，必须单独批准并准备回退。

用户不应把 AK、SK、模型 Key 等密钥发进聊天。密钥由用户录入本机环境、系统钥匙串或云平台 Secret。Agent 只检查存在性和权限，不回显实际值。

上线采用协助式模式。Agent 负责检查、方案、经批准后的命令、日志和排错。用户负责账号注册、实名、凭证录入、费用批准、必要控制台操作、正式发布批准和线上验收。默认终点是“可部署”，不是自动正式上线。

现有部署手册中“把 AK/SK 交给 AI”及广泛 `FullAccess` 的建议，不应作为产品工厂默认规则。产品工厂使用最小权限、短期凭证和显式授权。
